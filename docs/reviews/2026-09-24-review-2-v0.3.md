# HistoryMap — Review 2 of architecture v0.3

Reviewed: 24 September 2026 (reviewer: project owner). Recorded verbatim from the review conversation;
line references point to the v0.3 draft reviewed at the time.

---

**This revision is substantially stronger. I would proceed with the data audit, but fix several remaining contract issues before treating it as the implementation specification.** The overall architecture no longer needs redesign.

I reviewed the updated file, whose internal version is **v0.3**. The agreed categories, region, and time range remain unchanged.

The revision addresses the main concerns well: separate entities and events, typed relationships, full-catalogue loading, honest location handling, explicit border snapshots, and a first prototype focused on connected exploration. These are meaningful improvements.

**1. High: occurrence IDs still are not guaranteed to be stable.**
(Source: occurrence suffixes, v0.3 line 154)

The statement that suffixes such as `:2` "come from distinct Wikidata statements" does not explain how they remain stable when statements are reordered, added, or removed.

There is also a more important semantic problem: **two statements do not necessarily describe two occurrences.** They may report conflicting dates for the same destruction. Wikidata explicitly permits multiple values reflecting different sources, and query result ordering is not guaranteed. [Wikidata statement documentation](https://www.wikidata.org/wiki/Help:Statements).

I would require:

- Persisted occurrence keys, rather than numbering based on current query order.
- Source statement IDs retained as provenance.
- An explicit rule distinguishing repeated events from alternative claims about one event.
- Unresolved conflicting claims flagged for review rather than automatically turned into additional events.

Wikibase supplies unique statement identifiers, which can anchor source mappings, although an application event may ultimately combine several statements. [Wikibase JSON documentation](https://doc.wikimedia.org/Wikibase/master/php/docs_topics_json.html#autotoc_md_statements).

A useful test is: **reordering statements or adding another claim must not change existing event IDs or break curated links.**

**2. High: the date model is improved, but its rendering semantics remain contradictory.**
(Source: date rules, v0.3 line 160)

Section 4 says the render time is the uncertainty interval's midpoint. Section 8 says an event becomes active at `start.earliest`. The fade starts "after it ends," without specifying which bound is used.

For an uncertain point event spanning a century, this leaves several incompatible interpretations: appear at the earliest date, appear at the midpoint, or remain active throughout the uncertainty interval. That last interpretation would recreate the uncertainty-versus-duration problem.

Define these separately:

- The event's possible occurrence interval.
- Its representative position on the timeline.
- The rule for displaying it during playback.
- The reference time from which fading begins.

My suggested prototype default is to reveal uncertain point events at their representative time, clearly styled as uncertain, while showing their full possible interval on selection. That is a display convention, not a claim that the event happened then.

Two further corrections are needed:

- **Mixed calendars need a common comparison axis.** Preserve and display the original Julian/Gregorian date, but normalize computational values to one calendar or day-number system. "No conversion" is unsafe if numeric values from both calendars are compared directly.
- **The century example is off.** Wikidata interprets the twelfth century as 1101–1200, not 1100–1199. If the upper bound is exclusive, the corresponding year interval is `[1101, 1201)`. Specify inclusivity consistently. [Wikidata date documentation](https://www.wikidata.org/wiki/Help:Dates).

Finally, `end absent ⇒ point event` is too strong. A known duration with an unknown ending must remain distinguishable from a point event. This can be a small explicit field; it does not require a comprehensive temporal database.

**3. High: the marker budget can suppress visible events in favour of invisible ones.**
(Source: visibility rules, v0.3 line 269)

"Active" currently means "has started and passes category filters." Such an event remains active after fading to zero. The budget then selects the highest-priority active events.

Under that definition, old, fully transparent events can consume all 150 slots while newer visible events are suppressed.

Specify this order:

1. Determine temporal and category eligibility.
2. Calculate opacity.
3. Exclude unlocated, off-screen, and fully transparent candidates from the ordinary marker budget.
4. Rank the remaining candidates.
5. Apply selection-context exceptions separately.

Use an explicit ID tie-breaker so equal-priority events produce stable results.

The selection exception also needs boundaries. "Selected event and its related events stay visible regardless of budget" can produce hundreds of markers and arcs. Keep the selected marker visible, but limit displayed neighbours and provide a "show more" list.

Define how future related events and disabled categories behave. My recommendation is that future events appear in the panel and become visible on the map after an explicit time jump. Any context shown despite category filters should be visibly distinguished.

Also add **selection and selected sequence** to the determinism invariant. Both affect rendering but are missing from its listed inputs.

**4. High: the pipeline needs an explicit policy for scope and referenced records.**
(Source: pipeline and validation, v0.3 line 222)

Failing on dangling relationship targets is sensible, but the pipeline does not yet explain how it avoids creating them.

Examples include:

- An in-scope birth linked to a death outside the agreed period.
- An event linked to a participant whose own life events were excluded.
- A curated sequence containing an excluded or renamed event.

The agreed scope should govern which **events are eligible for the prototype**, while referenced entities can still exist as supporting records.

Specify that:

- All referenced entities needed to interpret retained events are included.
- Event-to-event links are retained only when their targets are available, or represented explicitly as external references.
- Omitted links receive an exclusion reason.
- Sequence steps, `subjectEntity`, and overrides are validated as well as relationships.

Regional filtering also needs an explicit rule for unlocated events. "No coordinates" does not establish that an event belongs inside the agreed region. Require other evidence of regional relevance or a reviewed inclusion.

**5. Medium: derived relationships could unnecessarily dominate the dataset.**
(Source: derived links, v0.3 line 192)

Avoid materializing a `sameConflict` relationship between every pair of battles.

For 1,000 battles in one conflict, that means **499,500 unordered links**, despite the underlying fact being just 1,000 membership relationships. This could undermine the otherwise sensible decision to load the full catalogue.

Store event-to-conflict membership and an index:

```text
conflict ID → member event IDs
```

Derive a bounded list of neighbours when an event is selected. Apply the same approach to shared campaigns and subjects.

Also distinguish **events about an entity** from **events involving an entity**. The proposed `bySubject` index handles the former. A polity chip should additionally find battles where that polity is a participant; those battles will usually have another subject.

**6. Medium: provenance is named but not yet specified enough to support corrections.**
(Source: event provenance, v0.3 line 148)

`Provenance` is referenced but never defined. A manifest-level retrieval date plus strings such as "Wikidata P361" will not reliably explain why a particular date or coordinate was selected.

Keep this lightweight, but define at least:

- Source entity and statement identifiers.
- Source revision or cached snapshot reference.
- Extraction rule/version.
- Applied override and its reason.
- Supporting URLs for curated interpretations.

Preserve raw inputs and record the extractor/configuration version so builds can be reproduced. A dated output directory alone does not make a build reproducible.

This is particularly important when an event's date comes from one claim, its coordinates from another entity, and its relationship explanation from a curator.

**7. Medium: quarter-year update buckets introduce avoidable playback compromises.**
(Source: performance strategy, v0.3 line 290)

A fixed `0.25-year` update interval means:

- At 1 year/second, opacity changes only four times per second.
- At 25 years/second, bucket boundaries occur 100 times per second, potentially more often than frames can be displayed.
- At day-level precision, event appearance can lag substantially behind the displayed date.

`updateTriggers` is a valid mechanism for refreshing attributes, but it does not itself provide a scheduling policy. [deck.gl layer documentation](https://deck.gl/docs/api-reference/core/layer#updatetriggers).

For the small prototype, start with animation-frame-driven playback and measure it. If needed, throttle expensive ranking independently from visual updates. Explicit seeking must always evaluate the requested time immediately.

**The milestones are now appropriate, with two small adjustments.**

First, the feasibility sample should be stratified across centuries and subregions and include difficult cases: missing locations, uncertain dates, conflicting statements, and sparse relationships. Sampling only convenient or prominent items would overstate feasibility.

Second, add a minimal event browser or searchable list to milestone 2. With fading enabled and the histogram deferred, users otherwise lack a dependable way to recover faded or unlocated events. This directly supports the proposed interaction test.

I would keep the suggested defaults: ghosts off, category-specific extractor code, and 150 ordinary markers as an initial experiment. I would also accept the birth/death connection as a derived `sameSubject` relation when both events are within scope. These do not need further architectural debate.

**My recommendation is to begin the audit now and resolve findings 1–4 before implementing playback and curation.** The revised structure is suitable for the proof of concept; the remaining work is to make its rules precise enough that different modules cannot interpret the same historical record differently.
